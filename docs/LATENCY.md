# Latency plan: hill-climbing time to first audio

Agreed on 2026-10-21. One hill-climb over the whole voice turn, following `/claude-api` build-eval and hillclimb.

## Starting point (Langfuse, 38 turns of manual testing)

| | p50 | p95 |
|---|---|---|
| Whole turn (today the first audio arrives with the whole turn) | 9.5 s | 16.4 s |
| TTS | 4.0 s | 11.2 s |
| LLM, per call (~1.6 calls per turn) | 2.5 s | 6.4 s |
| STT | 0.7 s | 2.0 s |

## Metric and goal

- **Time to first audio (TTFA):** server-side, from the moment the declarant's audio arrives to the moment the first audio chunk of the reply is sent. Network and browser are out.
- **Stop** when the eval reaches **p50 ≤ 4 s and p95 ≤ 7 s**, when the budget runs out, or after 3 rounds in a row without an improvement above noise.
- Every case also records the per-stage breakdown (STT, LLM, TTS to the first chunk), so the analyzer can pick the lever with the most impact and each improvement can be attributed to its change.

## Guardrails

- Extraction correctness, checked programmatically (no LLM judge), must not get worse.
- Off-limits: `domain/` rules, the invariants of ADR-0002 (code owns the flow) and ADR-0005 (critical messages from templates), and the existing tests, which must keep passing.
- Changing the TTS model or voice, or the LLM model, is allowed without asking as long as quality holds. The accent can't be measured by the eval, so each TTS voice or model change saves a listening sample in the report.

## Levers (starting order; the analyzer reorders them from measurements)

1. TTS by sentence, sending each chunk as soon as it's ready.
2. Cached audio for fixed templates.
3. Fewer LLM rounds per turn, and a streamed reply into the TTS.
4. Stable prompt prefix first, to benefit from the provider's prompt caching.
5. Shorter spoken texts, still generated by code (ADR-0005).
6. Another TTS or LLM model.

## Cases

Single turns: a claim state plus the declarant's next utterance, taken from the stored test conversations (the people and policies are the fictional seed data) and from audio clips: the nine in `tests/e2e/fixtures/audio/` plus the ones scripted in [evals/recordings.md](../evals/recordings.md).

## Budget

- **$0.30 in total**, on an OpenRouter key used only for evals and limited to $0.30.
- Pilot ≤ $0.01 to measure the real cost of one case. The rest goes to the baseline and the rounds; the runner stops by itself at $0.28.
- If the pilot shows fewer than 4 rounds fit, the runner replays recorded stages that a round's change doesn't touch (with their measured times) instead of paying for them again.

## Order

1. Run the eval baseline after the bug-fix branch is merged, so the baseline matches the code being tuned.
2. Pilot, then the eval cases (reviewed before any paid run), then the baseline, then the rounds.
